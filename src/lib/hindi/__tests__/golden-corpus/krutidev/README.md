## Known limitations (documented, not silently skipped)

- **No real deed sample (M2, partial).** A genuine property/registry deed
  is a private legal document (contains PII — names, addresses, survey
  numbers) and is not something obtainable by "download from the net"
  without violating someone's privacy; no client-provided sample exists
  either. Entry 01 is real, independently-sourced Hindi prose (not
  synthetic), which satisfies "real downloaded text," but it is not a deed.
  If/when a client provides a real deed excerpt, review it for PII
  (redact/replace names, addresses, property details with realistic
  placeholders that preserve the same linguistic patterns) before adding
  it here as entry 08+, per TESTING.md § 6.
- **Mixed Hindi/English is inherently one-directional (entry 07).** Kruti
  Dev is a single-byte legacy font where every ASCII character maps to
  *some* Devanagari glyph. Real Kruti Dev documents distinguish embedded
  English from Hindi via font-run switching (the English portion is set in
  an ordinary Latin font, only the Hindi portion in Kruti Dev) — plain text
  cannot carry that information. So `unicode_to_kruti` on mixed text is
  reliable (English passes through unchanged, tested here), but running
  the result back through `kruti_to_unicode` cannot recover the original —
  it has no way to tell "these letters are literal English" from "these
  letters are Kruti Dev codes that happen to look like English." This is a
  fundamental property of the plain-text conversion model, not a bug in
  this mapping; `krutidev.test.ts` documents it explicitly via an
  exceptions list rather than silently skipping or hiding it.
- **Entry 08's `unicode_to_kruti` direction is not exact-match tested.**
  The 5 rare conjuncts in entry 08 each have a dedicated single-byte Kruti
  Dev glyph (per SIL) *and* a general decomposed encoding (consonant +
  virama + consonant, this module's default for `unicode_to_kruti`) that
  render identically in the actual font. `krutidev.test.ts` tests the
  dedicated byte codes via `kruti_to_unicode` (that's the direction the SIL
  cross-check found missing); the decomposed encoding for the reverse
  direction was separately verified to round-trip correctly (see
  `mappings/krutidev.ts` header) but isn't asserted byte-exact here since
  it deliberately doesn't reproduce the specific rare byte.

## Growth process

Every Hindi conversion bug fix adds a new corpus entry reproducing the bug
before the fix is considered complete (AI_RULES.md rule 12). Corpus only
grows; entries are never deleted, only superseded if a mapping table is
deliberately revised (with a note explaining why). Corpus tests run in CI
on every PR touching `lib/hindi/**` — a single failing entry blocks merge.
